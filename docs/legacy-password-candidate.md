# 旧版机器密码候选命令

依据是当前已修改旧包源码（SHA和函数位置见evidence/legacy-password-candidate-2026-10-07.json），不是实际蓝牙记录，也不证明命令用途或设备执行。

`setBleConPwd`从globalData.pwd六项读取数值，数组声明opcode=11、第二项=6、六位密码和末尾0。生成十六进制串时只循环前八项，然后调用BleWrite(hex,9)。BleWrite把字符串传给hexStringToArrayBuffer，该转换器先分配9字节ArrayBuffer，填入已有8字节；新缓冲区默认零初始化，末尾保留零。

因此合法六位十进制输入下，候选写入缓冲区是9字节：`0B 06 d0 d1 d2 d3 d4 d5 00`。密码位是0..9的数值，不是ASCII；没有额外XOR。不能仅因为编码串8字节、请求长度9字节就推断末字节丢失或长度矛盾。不要根据其它命令的规则补校验。

离线工具只提取并执行已锁定源码的三个函数，BleWrite替换为内存校验，不执行App/bundle/UniApp/BLE。覆盖000000至999999全部一百万组合，每组分别用字符数组和数字数组输入，共两百万缓冲区对照全部通过。没有记录任何实际密码。原始拆包未修改文件也已静态核对同样的8字节编码、9字节分配和转换规则，SHA记录在证据rawCorroboration；该原始副本没有执行，不能把两百万结果称为两套源码运行。新原生App仍使用Kotlin；此Node工具仅供旧源码取证，不是产品运行依赖，也不在APK中执行。

源码全局setBleConPwd符号只发现一处声明，当前www的JS/HTML搜索也仅命中该声明，未找到直接静态调用。这不排除动态、远端或其它版本调用，不能据函数名推断有可用的“修改密码”页面，也不能据无直接调用断言厂商设备不支持。

## 保持关闭的原因

机器改密后的确认、新旧密码重连、断线/超时与用户恢复路径均无真实序列。这个候选缓冲区不证明密码修改或校验语义，不应给当前1.1.3机器试发。原生保持无编码/执行入口，GuardedGattDriver继续拒绝0x0B；拒绝测试增加这个完整9字节候选，要求实际fake driver零调用。

CoffeeCredentialStore保存已验证的连接密码只是本机加密记忆，与修改机器密码不同。只在取得对应固件真实修改/确认/重连/失败恢复样本后，才能规划开放流程；现阶段未实现此功能，仍保留在整体对标缺口。
