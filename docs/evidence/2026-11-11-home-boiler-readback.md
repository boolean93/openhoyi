# 首页锅炉开关回读：协议依据与修复边界

基线：`develop e7c7ac8a`。用户反馈“开关锅炉……回读不会自动刷新”，要求修复首页开关。第一轮实现未连接实体咖啡机；第二轮经用户授权覆盖安装并只读启动，取得实际连接报告，未代用户开关锅炉或发起萃取。

## 已确认的原因

- `HomeFragment` 可见时每 250 ms 从服务快照重绘，开关读取 `Settings.brewHeating/steamHeating`，并非漏掉页面刷新定时器。
- `MobileService.changeMachineSetting` 在控制写入的 GATT 回调成功后进入 `WAITING_READBACK`。只有之后的新 `0x83` 主设置帧匹配目标，才确认并解除写入保护；6 秒收不到则进入 `UNKNOWN`。这一保护不能改成“写出去就成功”。
- 但目前锅炉开关只发送 `0C 02 00 en 00` / `0D 02 00 en 00`，不触发新的设置同步；而固件不会因此主动发送主设置帧。

## 官方 App 与固件证据

官方 HOYI 1.2.6 APK SHA-256：`26133c2ac8ecf3d5ee7682bafa6555b1c78836749c937477b05214a88d8ea238`。

其 `app-service.js` 中：

- `setTempPowerEn`（字节偏移约 1572857）和 `setSteamPowerEn`（约 1573061）分别只发送上述 5 字节控制帧。
- `brewTemp` / `steamTemp` 组件点击时先赋值 `globalData.brewEn/steamEn`，再发送命令，属于本地乐观更新，不是设备确认。
- `checkTime`（约 1561757）发送既有 15 字节 `0x01` 认证/校时帧。主设置回读里的 flags bit 5 / bit 4 分别映射两种加热允许状态。

固件 1.1.4 SHA-256：`fa869de17b99836d5962d0566e93f543765194be2885265df514cd9a27dfc8aa`。地址对应现有 `application-prefix.thumb.txt`：

| 地址 | 行为 |
| --- | --- |
| `0x08010BA0–0x08010BBC` | `0x0C`：保存萃取锅炉开关到 `S+0x2AF`，调用 EEPROM 写入，再跳通用收尾；不发主设置帧 |
| `0x08010BBE–0x08010BDA` | `0x0D`：保存蒸汽锅炉开关到 `S+0x2B0`，同样不发主设置帧 |
| `0x0800F9AE` | 构造并发送 `0x83` 主设置帧；两种开关来自上述存储字段 |
| `0x0800FF48–0x0800FF90` | `0x01`：校时，然后在 `0x0800FF84` 调用主设置帧发送，重置睡眠分片发送位置 |
| `0x08010F8E` | 另一处主设置帧发送来自滤芯设置。不能为获取回读而发送无关设置 |
| `0x08010FA4` | `0x40` 仅开启遥测发送标记；不是已证实的主设置查询指令 |

在该镜像内主设置构造器只有上述 `0x01` 与滤芯设置两处直接调用，锅炉开关及常规遥测循环均无调用。不能凭空新增所谓“只读查询 opcode”。

既有 1.1.3 实机记录 `1789783373182-0da5ffdc-0.jsonl` 的 seq 16055、16575、16636、17295 是萃取锅炉关/开命令。从这些命令之后至该记录结束没有 `0x83` 通知，仍有持续 `0x40` 遥测。它佐证“等下一条周期设置回读”不可靠，但不是本次修复的实体设备验收。

## 首次安装后的真实失败（1.1.3）

首次修复只在 GATT 成功后立即发一次同步，fake-GATT 通过，但没有覆盖“刷新 GATT 成功、设备不回报告”的真实情况。用户重复开关后仍卡未知，不能把这次测试成功当成原方案足够可靠。

真实平板 `trace-00000000000000000081.jsonl`，固件 `0x83 01 13`（1.1.3），同一个服务 owner / generation 1：

| UTC 时间 / seq | 操作 | 刷新及实际结果 |
| --- | --- | --- |
| 13:48:50.708 / 36 | 萃取关 | 控制后45ms发同步；52ms后新主设置，确认 |
| 13:49:00.655 / 58 | 蒸汽关 | 控制后50ms发同步；60ms后新主设置，确认 |
| 13:49:15.233 / 86 | 萃取开 | 控制后39ms发同步；59ms后新主设置，确认 |
| 13:49:20.770 / 103 | 蒸汽开 | 控制后36ms发同步；107/108/109均 request/accepted/completed status=0，但无主设置或睡眠分片回复；116在6秒后UNKNOWN |

第四次刷新时最新 idle 约121ms，并非1500ms新鲜度、owner或连接代次拒绝。之后持续 `0x40`，没有新 `0x83`，用户点击核对仍得到 seq121 `settings.recovery_waiting`。因此可以确认“传输成功但本次设备报告未到”，不能仅凭这一层日志断言 UART 丢帧或固件忙就是唯一根因。

1.1.4 静态镜像中锅炉 EEPROM 写入 helper 尾部存在 busy-wait，接收处理也有共享缓冲清理；这只是同系列的时序风险佐证，不是1.1.3这次未回复的唯一根因证明。

## 第二轮有界恢复与安全边界

- 原锅炉 `0x0C/0x0D` 仍只发一次。GATT 成功后进入原 WAITING/watchdog，首次认证/校时同步延迟250ms；1250ms仍未收到可闭合的新主设置时，最多补一次同步。250ms是保守工程间隔，不宣称固件保证。若第一笔同步晚发，实际两次同步也至少相隔250ms；截止仍是原成功写起6秒，不重启 watchdog。
- 缺少新鲜安全 idle 时等待新报告，不忙循环；同设备、同连接代次、原事务 owner/token、无萃取（含UNKNOWN）、手动萃取、预热或其他写冲突，队列出队前重检。每次同步结果写入 `settings.refresh`，传输成功不等于设置生效。
- 两次同步都未收到可闭合回报，约3秒允许原咖啡机一次窄重连。先消费 fallback 并撤销旧代同步，用会话内原密码和当前时间进入既有认证流程，不走会取消预热或允许未知萃取恢复的通用连接入口，不重复锅炉控制。
- Hub 的 `BoilerReconnectLease` 只抑制本事务被普通自动重连无限接管，不更改用户持久自动连接偏好；有效确认/对账闭合或用户显式新连接才解除。原写 watchdog 6秒不变；这次重连另有原成功写起18秒绝对上限，只结束仍归本事务所有的未READY初始化，不打断用户新连接、活跃萃取或预热。到期仍未知则保留记录。
- 原 owner 和原设备有效、该事务已经实际派发同步后，新主设置匹配目标才显示确认；真实值不符则仅针对本内存可识别的锅炉变更置 RECONCILED，清本 owner 已有真实报告的记录，明确显示“重试开启/重试关闭”，不是成功，也不自动重发。同步尚未派发前的无关相反报告不作为失败闭合。普通设置、跨 owner 或重启后的泛化SETTING记录不自动清。
- 同一已认证会话的锅炉UNKNOWN可由用户点“刷新状态”，只有一次同步、固定6秒期限和busy防抖，不发锅炉命令、不要求180秒设置新鲜度，但保留新鲜安全 idle 与原owner/device门禁。重启后缺少typed provenance时不启用这条捷径；用户仍需正常连接及显式核对。
- 首页两锅炉改为直接单击，执行中原位“开启中/关闭中”，恢复时“重连中/同步中”，不新增等待行。仅本锅炉原owner有效的正常WRITING/WAITING或有界恢复阶段，暂不展示它自己的泛化红条/核对按钮；其他萃取、报警和未知写风险照常显示，预算耗尽后未知风险重新明确展示。
- 没有纯只读查询：所有同步仍是既有15字节 `0x01` 认证/校时，有更新机器时钟和重启设置/睡眠分片回报的副作用；凭据脱敏，结束连接时清除。原出站白名单、物理控制及未知结果门禁未放宽。
