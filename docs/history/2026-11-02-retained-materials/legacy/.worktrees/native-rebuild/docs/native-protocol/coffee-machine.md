# 咖啡机 BLE 协议

## 1. 发现与 GATT

**C1 已确认**

| 项目 | 值 |
|---|---|
| 广播名 | 名称包含 `HOYI`，忽略大小写 |
| Service | `55535343-FE7D-4AE5-8FA9-9FAFD205E455` |
| Write | `49535343-8841-43F4-A8D4-ECBE34729BB3` |
| Notify | `49535343-1E4D-4BD9-BA61-23C647249616` |
| 扫描窗口 | 5 秒 |
| 连接超时 | 22 秒 |
| 连接后发现服务 | 延迟 2 秒 |
| Notify 重试 | 最多 2 次，间隔约 400 ms、800 ms |
| 写失败恢复 | 重新发现服务/特征后重试 1 次 |

UUID 比较时应统一转为小写并去掉连字符。旧应用没有真正的周期保活；`startKeepAlive()` 只会清理旧定时器。

Android 侧连接成功不能等同于协议就绪。完成服务发现、写特征确认和 CCCD 订阅后才进入 `Ready`。首次收到普通 `0x83` 设置帧后，才可认为设备状态已经同步。

## 2. 帧的一般规则

**C1 已确认**：接收端以 byte 0 分派。旧应用没有通用帧头、通用长度字段和通用校验。

下行命令经常采用：

```text
[opcode, payloadLength, payload..., trailer]
```

但并不统一：部分 5 字节命令末尾固定 `0x00`，部分命令末尾是前面字节的 XOR，曲线和 OTA 又有独立格式。因此 Native 代码应为每种命令单独编码，不要写一个假设所有命令同构的通用 encoder。

所有多字节整数除特别注明外均为大端序。旧应用把每次 notification 当成完整帧。新实现应记录异常长度；只有抓包证明存在分片后，才按确认的规则组帧。

## 3. 上行帧

### 3.1 `0x83` 设备设置

普通设置帧满足 `byte[0] == 0x83 && byte[1] < 0x40`。

| 偏移 | 含义 | 换算 | 可信度 |
|---:|---|---|---|
| 0 | 消息类型 | `0x83` | C1 |
| 1 | 固件主版本 | 无符号 byte | C1 |
| 2 | 固件次/修订版本 | 高 4 bit / 低 4 bit | C1 |
| 3 bit7 | 压力逻辑开关 | bool | C1 |
| 3 bit6 | 流量逻辑开关 | bool | C1 |
| 3 bit5 | 萃取锅炉加热 | bool | C1 |
| 3 bit4 | 蒸汽锅炉加热 | bool | C1 |
| 3 bit3 | Barista 灯 | bool | C1 |
| 3 bit2 | 运行模式 | bool；具体枚举需产品确认 | C2 |
| 3 bit1 | 供水模式 | bool；旧 UI 映射水箱/管线 | C2 |
| 3 bit0 | 睡眠计划总开关 | bool | C1 |
| 4 | 萃取设定温度 | °C，整数 | C1 |
| 5 | 萃取温度补偿 | `raw × 0.1 °C` | C1 |
| 6 | 蒸汽设定温度 | °C，整数 | C1 |
| 7 | 待机时间 | 分钟；已见 0/15/30/60/120 | C1 |
| 8 | 待机温度 | °C，整数 | C1 |
| 9..10 | 萃取杯数 | `u16 BE` | C1 |
| 11 bit1 | 水箱滤芯已安装 | 固件整数版本 `>= 276` 时有效 | C1 |

固件字符串为 `byte1.(byte2 >> 4).(byte2 & 0x0F)`；代码同时用 `(byte1 << 8) | byte2` 做能力判断。

`0x83 0x40 ...` 与 `0x83 0x80 ...` 是睡眠计划回读：

- `0x83 0x40 flags sunday[4] monday[4] tuesday[4] wednesday[4]`
- `0x83 0x80 thursday[4] friday[4] saturday[4]`
- 每天 4 字节依次为睡眠小时、睡眠分钟、唤醒小时、唤醒分钟。
- `0x40` 帧的 byte 2 是启用位图：bit6～bit2 对应周一～周五，bit1 对应周六，bit7 对应周日。

这里的星期顺序来自页面数组读写，属于 **C1**；帧是否还有尾部校验未知。

### 3.2 `0x40` 空闲遥测

| 偏移 | 含义 | 换算 | 可信度 |
|---:|---|---|---|
| 0 | 消息类型 | `0x40` | C1 |
| 2..3 | 萃取温度 | `u16 BE / 100 °C` | C1 |
| 4..5 | 蒸汽温度 | `u16 BE / 100 °C` | C1 |
| 6 | 萃取锅炉压力 | `raw / 10 bar` | C1 |
| 7 | 蒸汽锅炉压力 | `raw / 10 bar` | C1 |
| 8 | 睡眠状态 | `1` 为睡眠 | C1 |
| 12..13 | 报警位图 | `u16 BE` | C1 |
| 14..15 | 萃取杯数 | `u16 BE` | C1 |
| 16..17 | 系统信息页额外传感值 | 具体物理量未确认 | C3 |

报警位图按 bit 0 起映射到 C1、C2……。旧应用显式使用了 bit1/C2、bit9/C10、bit12/C13。代码还展示 C16 文案，但常规循环只检查到 bit14，需真机制造或回放故障帧验证完整位数。

页面显示的萃取温度会再减去 `0x83` 中的温度补偿；协议解析层应保留原始测量值，补偿属于业务/展示规则。

### 3.3 `0x80` 萃取遥测

| 偏移 | 含义 | 换算 | 可信度 |
|---:|---|---|---|
| 0 | 消息类型 | `0x80` | C1 |
| 2 | 当前曲线槽/阶段 | 常见 1～8；6、7 被旧代码视为手动模式 | C2 |
| 3..4 | 已萃取时间 | `u16 BE`，秒 | C1 |
| 5 | 萃取压力 | `raw / 10 bar` | C1 |
| 6..7 | 累计水量 | `u16 BE / 10 ml` | C1 |
| 8..9 | 萃取温度 | `u16 BE / 100 °C` | C1 |
| 10 | 瞬时水流 | `raw / 10 ml/s` | C1 |
| 11 bit6 | 阀门开启 | bool | C1 |
| 11 bit5 | Brew wait 阶段 | bool | C1 |
| 11 bit4 | 压力反馈/模式 | bool，精确名称待验证 | C2 |
| 11 low nibble | 曲线/控制状态 | 旧代码只判断是否非零 | C3 |
| 12 | 手动拉杆/阶段值 | `0xFF` 无效，完整语义待验证 | C3 |

旧应用为了兼容旧固件，在 byte 11 的 bit5/bit6 都不存在时，会依据压力、流量、时间和累计水量猜测“正在萃取”。这是业务状态推断，不是协议字段。Native 解析层只输出帧字段，由萃取会话状态机决定开始与结束。

旧状态机的参考阈值：手动槽 6/7 使用压力 `> 0.05 bar` 或流量 `> 0.05 ml/s`；其余槽使用压力 `> 1 bar` 或流量 `> 0.8 ml/s`。最后活动帧 450 ms 后尝试结算，900 ms 内仍视为近期活动。以上均为 **C2 业务规则**，迁移前应以真机体验重新标定。

### 3.4 OTA 上行

| opcode | 旧应用解释 | 可信度 |
|---:|---|---|
| `0xA0` | byte3=`1` 已接受并保持；其他为进入失败 | C2 |
| `0xA1` | byte3=`1` 备份中，`2` 无应用，其他为备份完成 | C2 |
| `0xA2` | 回滚状态，分支与 `0xA1` 类似 | C2 |
| `0xA4` | byte3=`1` OTA 成功；其他失败 | C2 |
| `0xA5` | bytes2..3 为设备请求的下一个 block，`u16 BE` | C1 |

OTA 涉及固件安全，首版 Native 应先做只读识别，不在没有抓包和可恢复方案时开放升级。

## 4. 下行命令

### 4.1 时间认证与状态命令

| opcode | 命令 | 字节布局 | 可信度 |
|---:|---|---|---|
| `0x01` | 校时/密码认证 | `[01,0C,yy,MM,dd,HH,mm,ss,pwd×6,xor]`，共 15 字节 | C1 |
| `0x03` | 压力/流量逻辑 | `[03,02,pressure,flow,00]` | C1 |
| `0x04` | 萃取温度 | `[04,02,valueHi,valueLo,00]`，调用值为整数 °C | C1 |
| `0x05` | 萃取温度补偿 | `[05,02,valueHi,valueLo,00]`，调用值为 `补偿°C × 10` | C1 |
| `0x06` | 蒸汽温度 | `[06,02,valueHi,valueLo,00]`，调用值为整数 °C | C1 |
| `0x07` | 蒸汽偏移/档位 | `[07,02,a,b,00]`，参数语义待确认 | C3 |
| `0x0A` | 清零杯数 | `[0A,01,A5,A5,00]` | C1 |
| `0x0C` | 萃取加热 | `[0C,02,00,enabled,00]` | C1 |
| `0x0D` | 蒸汽加热 | `[0D,02,00,enabled,00]` | C1 |
| `0x0E` | Barista 灯 | `[0E,02,00,enabled,00]` | C1 |
| `0x0F` | 运行模式 | `[0F,02,00,value,00]` | C1 |
| `0x10` | 供水模式 | `[10,02,00,value,00]` | C1 |
| `0x11` | Brew wait | `[11,02,00,value,00]` | C1 |
| `0x12` | 排水模式 | `[12,02,00,value,00]` | C1 |
| `0x13` | 开始/结束排水 | `[13,02,00,value,00]` | C1 |
| `0x14` | 待机设置 | `[14,02,minutes,tempC,00]` | C1 |
| `0x15` | 睡眠计划总开关 | `[15,02,00,enabled,00]` | C1 |
| `0x16` | 拉杆零点校准 | 旧代码编码 `16 01 A5 A5` 却请求写 5 字节 | C1 缺陷 |
| `0x17` | 恢复出厂 | `[17,02,00,value,00]` | C1 |
| `0x17` | 忽略报警 | `[17,alarmIndex,A5,00,xor(first4)]` | C1，opcode 冲突需真机验证 |
| `0x18` | 水箱滤芯 | `[18,02,00,enabled,00]` | C1 |
| `0x20` | 立即睡眠 | `[20,01,A5,A5,xor]` | C1 |
| `0x21` | 萃取提示灯 | `[21,02,00,value,00]` | C1 |
| `0x40` | 数据确认 | `[40,01,A5,A5,xor]` | C1 |

`0x0B` 修改 BLE 密码存在明确旧代码缺陷：逻辑分配 9 字节 `[0B,06,pwd×6,00]`，但只编码前 8 字节十六进制，却向底层声明长度 9。Native 版必须通过抓包确认设备实际期望 8 还是 9 字节，不能照搬。

### 4.2 睡眠计划 `0x09`

- 单日格式：`[09,05,day,sleepHour,sleepMinute,wakeHour,wakeMinute,00]`。
- 批量前四天：`[09,10, day0×4, day1×4, day2×4, day3×4, 00]`。
- 批量后三天：`[09,0C, day4×4, day5×4, day6×4, 00]`。
- 批量格式把睡眠小时的 bit7 用作该日启用标记；小时值位于低 7 bit。

单日格式的 `day` 编号和是否带启用位没有足够调用证据，标为 **C3**。

### 4.3 曲线启动 `0x02`

停止命令为 `[02,00,slot,00,00]`。

启动曲线为 20 字节：

| 偏移 | 含义 |
|---:|---|
| 0 | `0x02` |
| 1 bit7 | 压力逻辑 |
| 1 bit6 | 曲线/可变流量逻辑 |
| 1 bits5..3 | 分段数量 |
| 1 bits2..0 | 设备槽位，常规 1～5，临时/自定义路径使用 7 |
| 2 | 萃取温度 °C |
| 3..4 | 最大水量，`u16 BE`，单位由 UI 视为 ml |
| 5 bit7 | 第一段流量模式 |
| 5 low7 | 闷蒸/预浸秒数 |
| 6..9 | 四段目标值；压力模式通常为 `bar × 10`，部分流量模式复用 |
| 10..11 | 第一段流量/水量参数，`value × 10`，`u16 BE` |
| 12 | 第一段持续时间，秒 |
| 13..14 | 第二段流量/水量参数，`value × 10` |
| 15..16 | 第三段流量/水量参数，`value × 10` |
| 17..18 | 第四段流量/水量参数，`value × 10` |
| 19 | bytes0..18 XOR |

如果电子秤已连接，旧应用会根据目标杯重提高最大水量下限。这是业务策略，不属于协议编码。

`0x08` 同时存在“复制曲线到机器”的 20 字节格式和一个旧版 14 字节 `setChart` 格式。新项目首版只实现经真机验证仍在使用的路径，避免凭 opcode 猜格式。

### 4.4 OTA 下行

| 命令 | 布局 |
|---|---|
| 进入 OTA | `[A0,04,48,4F,59,49,xor]`，中间是 ASCII `HOYI` |
| 文件长度 | `[80,AA,len32BE,xor]` |
| 重置应用 | `[80,AB,48,4F,59,49,xor]` |
| 数据块 | `[blockIndexBE,data最多17字节,xor]` |

校验是对校验字节之前所有字节 XOR。块大小、重传、完成条件仍需设备抓包和可恢复测试。

## 5. Native 实现前必须补的抓包

1. 正常连接后完整记录 `0x83`、至少 30 秒 `0x40`、一次完整萃取的 `0x80`。
2. 分别修改温度、补偿、蒸汽温度、待机、睡眠计划，验证设备回读。
3. 验证 `0x0B`、`0x16` 的实际写入长度，以及 `0x17` 两种命令的区分规则。
4. 抓取通知 MTU 与 notification 边界，确认一帧是否可能拆分或合并。
5. OTA 单独安排，可恢复性确认前不写设备。
