# 旧版萃取提示与提示灯

依据：拆包 `app-service.js` 的设置页、鼓励音频模块、蓝牙编码及首页萃取结束逻辑。可复查的源码SHA、行号和静态候选帧见 `evidence/legacy-brew-preferences.json`。这不是实际设备记录，也不证明固件执行或正确恢复。

| 项目 | 已确认的旧版行为 | 原生边界 |
|---|---|---|
| `brewTips` | 设置页开关只存本地布尔值；消费侧控制鼓励弹窗/音频是否触发。开启后，音频播放还可能通过提示灯偏好引发设备命令 | 尚未实现完整提示/音频体验；不能把该开关整体称为纯UI |
| `brewTipsLed` | 本地控制播放/停止鼓励音频时是否调用 `setBrewEncourageLed`；偏好版本不是2时旧版会强制初始化为开启 | 原生没有自动提示灯写入入口；不复制强制开启/自动发送 |
| `setBrewEncourageLed(level)` | 构造5字节 `21 02 00 level 00` 并交给 `BleWrite`，不是普通照明 `Light` 的设置命令 | 登记为 `UnsupportedCommandGroup.BREW_ENCOURAGEMENT_LED`，只描述边界，无编码/发送API |

音频模块将播放等级限制在0..2，并在停止时发255。静态候选帧为 `2102000000`、`2102000100`、`2102000200`、`210200FF00`。旧转换器只将十六进制截取为指定长度的缓冲区，没有补算校验；最后的零来自该命令自身，不能擅自套用其它命令的XOR规则。

`BleWrite` 的失败分支还可能重新发现服务并重试一次。这是旧版路径，不应据此给原生未确认写入增加自动重试。

首页 `tryShellBrewEncourageShow` 受 `brewTips` 和本杯已播放标志控制，要求记录时长大于14秒，按机器累计流量/时间启发式与2.2、1.5阈值决定等级并播放（不是秤重）。其它页面也调用同一音频模块。此启发式不是萃取质量证明，不应混同于目标重量自动停止或机器结束确认。

## 后续开发

本地提示/音频可作为独立展示功能规划，提示灯必须单独取证：固件/型号、四等级真实写入及通知、灯效是否自行结束、停止/断线/切换App后能否恢复、与普通照明及睡眠是否互相影响。取证完成前不新增发送入口。不得通过提示偏好更改启动资格、目标重量、停止逻辑或安全记录。

当前代码的Unsupported枚举是文档边界，不是能拦截任意低层字节的通用防火墙；原生之所以不会发这组命令，是没有编码和调用入口。本轮不声称完成灯效功能或硬件风险验证。

后续发送边界补充：所有DeviceSession路径现已接入GuardedGattDriver，格式策略也拒绝0x21鼓励灯命令（与十进制21/0x15睡眠计划启用命令不同）。Unsupported枚举本身仍只是文档；另起裸驱动不在包装器保护范围。详见plans/outbound-write-boundary.md。

## 进一步核对：本地提示的数据与播放结束

`progressFromRx`明确从0x80字节3..4读取秒数、字节6..7读取累计流量并除10。首页把最终累计流量和萃取阶段≤10秒时的快照传给提示函数，曲线的time参与分母：

`rate = (finalTotalFlow - earlyFlowSnapshot) / max(1, brewSeconds - curve.time - 10)`

仅时长>14秒且偏好开启、本杯未播放时触发。rate>2.2为等级1，rate≤1.5为等级2，其余为等级0；无效数字产生NaN也会落进等级0。它既不是秤流速，也不是杯中萃取率或咖啡质量的可靠判断。未来原生本地提示须明确数据有效性、同杯快照归属，不把这套启发式用于启动许可、停止控制或安全记录清除。

音频cf32模块先播放等级0的1.mp3或等级1/2的2.mp3，再从该等级四条英语语音中随机播放一条。自然onEnded/onError只清理音频对象并推进下一段，未调用setBrewEncourageLed(255)；255在显式stopBrewEncourageAudio中发送。不能仅凭“播放结束”推断旧代码已复位机器灯效，也不能据此推断固件灯效一定不会自行结束。原生仍无0x21编码/发送入口，真实灯效恢复须单独取证。

上述新增位置和规则已登记同源SHA256证据JSON，没有执行旧JS或操作设备。本地提示/音频尚未开发，当前仅把关键语义查清，未宣称完成原版体验。
