# 工作室自动预热：实现规划与协议证据

- 需求与范围：仅实际使用曲线时自动预热，覆盖曲线库、快捷槽位、上一杯；离页取消；咖啡馆模式不变。按钮附近显示可信实测温度与进度，区分请求、确认、失败，不自动发起真实萃取。
- 来源分支/基线：origin/develop，`5a765743a502ad03036a56c517fd211d2878edc5`；提交前已同步到 `e6440ed6`（#81）。
- 工作分支：`feature/studio-auto-preheat`；独立 worktree `openhoyi-preheat`。
- PR目标：develop。遵守 [Git工作流](../git-workflow.md)。已有 `.githooks` 配置未改变。
- 推送与合并：用户确认安全语义后实现，相关本地检查通过后经 `scripts/create-pr` 建 draft，独立复核、精确源码必需 CI 通过后 ready/合并。
- 发布：不发版、不安装、不操作机器，不涉及签名或升级。

## 已确认实现方案

用户在协议调查后选择方案A（按钮内温度进度、深灰圆角Toast），明确要求：离页时连接与机器状态正常安全才发一次取消；连接异常不做任何机器操作，重连后不补发。不承诺设备已取消。

- 曲线库使用、快捷槽位、上一杯显式使用触发；仅浏览/编辑/通用页面导航不触发，旋转重建不重发。温度未知时提示获取温度并重新使用，不挂隐式延迟启动。
- Service持有一次自动意图、原连接代次、配置revision、准备requestId；离页消费一次，正预热立即失去许可。取消提交和出队均查身份、配置、未见萃取、当前安全门禁，出队许可最长1500ms。看到萃取或断连不可逆失效，重连不恢复。
- 10分钟自动预热超时走同一受限取消入口，不使用不带归属的旧手动取消路径。取消写入保留CANCEL_WRITTEN与持久安全记录；不关锅炉、不写入旧目标。
- UI使用新鲜补偿温度与本次起始温度计算细进度；降温未达标不显示完成；缺测不显示数字进度或ETA；“温度准备”不等于设备执行确认。Mock可显示模拟取消完成，真实只显示请求与核对提示。
- 咖啡馆继续原流程；温度已就绪的一键萃取沿用原许可；需要预热则结束本次一键启动意图，达到温度后由用户显式开始。
- 本地纯单测/完整verify、独立Astra复核、专用手动CI Mock服务与UI运行截图；不在用户真实机器执行或安装。当前可用平板已有真实/Mock应用，本轮不覆盖安装，设备图由隔离CI模拟器生成。复用既有Mock工作流的preheat_checks手动入口，不扩大每次PR自动矩阵。

## 初次调查结论（用户确认较弱取消语义之前）

## 已查入口及后续设计约束

- 曲线库 `CurveFragment.kt:561–564`；独立旧Activity `CurveActivity.kt:453`；快捷槽与上一杯 `MainActivity.launchHomeCurve/openLastCurve`。不可在通用 `showExtraction`、Fragment重建或恢复时隐式开始，否则浏览/恢复也会触发。
- 一键萃取已有 `ShortcutStartPermit`；不能跨预热等待自动复活已过期启动许可。
- 温度规则沿用 `BrewTemperaturePolicy`：补偿后温度与目标相差不超过1°C，仍需新鲜数据及其它启动门禁。高于目标超过容差必须“等待降温”，不能用 `current/target` 截断到100%暗示可萃取。
- 未来进度应基于本次可靠起始温度到目标的温差，目标变化重新计算；未知/过期不显示数值进度或预计时间。真实协议未确认前文案只能“请求发送中／命令已写入，等待温度”，不能冒称“设备已确认预热”。

## 初次建议（现已采用第二项）

1. 保持原验收要求：先补固件活动目标、取消确认和操作归属证据/协议；在项目安全约束下单独安排必要硬件验证。

### 新回读字段核实

原始1.1.4反汇编 `application-prefix.thumb.txt:17291–17301`（0x0800F70C）明确从S+0x130生成0x80状态bit5；`deep/curve-report.md:54`将该字段定位为闷蒸停泵。不是S+0xD6预热状态，不能拿现有属性名brewWait当作预热取消ACK。0x40 b1来自S+0x53>1（17451–17461），尚无证据关联到D6或预热操作，不启用推断。

到温后D6变为3（16831–16835、16880–16882），并非变0；正常主循环仅D6==0时才恢复F8→F0（17120–17130）。因此“到温了”“收到待机了”不意味着预热已经自然撤销。未证明断链会自动取消，不能将重连当成复位。

0x11(0)除了恢复目标还调用0x0800878C(0)，这是泵控制输出归零路径；不是锅炉开关。迟到取消可能干预萃取，必须保留提交和实际出队双重萃取门禁，已进入萃取时撤销页面取消意图，不追加取消/停泵。

### 可实现的保守方案（待主会话确定验收语义）

1. **最强可证明分支**：若服务能够证明正预热命令从未提交给传输层，离页只撤销队列许可，展示“准备已取消”；这仅证明未执行本次预热，不宣称机器其它加热已停止。必须增加明确的dispatch事实记录，不能将任意失败都归类未发送。
2. **已发送分支**：同一连接、同一服务会话拥有的预热，在新鲜清醒待机且无萃取/其它控制变化时，离页发送一次0；状态留在“取消请求已写入，需核对机器”。无独立ACK则不自动清持久记录、不自动再开始另一条曲线。
3. **手动变化**：观察到机身/其它来源设置、模式或萃取变化，立即撤销本地自动启动许可；不回写进入页面的旧温度、不关原锅炉、不恢复旧开关。外部改变可能尚未回报，故只能减少风险，不能保证取消不覆盖外部临时目标。
4. **断连/重启**：同机重新认证并取得新鲜设置/待机，仅更新事实显示；保留未知记录，不重发正预热、不补发历史取消、不恢复旧目标。提供明确“检查机器”“发送取消请求”和“已核对安全”动作；异机不允许处理旧记录。
5. **温度UI**：发出前“正在发送预热请求”；写入成功“温度准备 89 / 92℃”，附简短“请求已写入”；新鲜补偿温度达±1°C只能叫“温度已达标”。没有加热执行确认，不称“已确认预热”。缺温度“正在获取温度”；过高“等待降温”；断连/失败保留对应文字、隐藏确定进度。
6. **锅炉关闭**：已有设置回读可显示关闭，但不为了自动预热擅自打开/恢复锅炉；提示开启后重新使用曲线。设置回读可观察变化，不能保证没有尚未回报的机身操作。

完整无人工干预的可靠恢复仍需设备侧返回临时目标、预热状态与可关联的操作版本/取消确认，或具备设备端超时租约/条件取消。只增加客户端计时、温度趋势或多帧待机不能补齐这些事实。
